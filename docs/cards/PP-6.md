# PP-6 One-command demo

## Goal
Everything PP-1..PP-5 guarantees, shown in one run a stranger can copy: eight labelled scenarios, printed in a fixed order, each one checked by the demo itself (not just printed). Red tests (`src/test/java/com/example/payplat/demo/*`) are architect-owned: do not edit them. If a test seems wrong, report instead of editing. Do not edit PP-1..PP-5 tests. Do not change PP-1..PP-5 behaviour: the demo only composes existing services (`PaymentService`, `JobWorker`, `CallbackService`, `StatusCorrector`, `RecoveryService`, `ReconciliationService`, `MonitoringService`, `SwitchLog`, `Router`).

## Run contract
- `./mvnw -q spring-boot:run -Dspring-boot.run.arguments=demo` and `make demo` (Makefile target `demo` calls exactly that command; also add a `test` target running `./mvnw -B test`).
- The demo is activated ONLY by the non-option argument `demo`. Without it the application starts exactly as before.
- Exit code 0 when all scenarios pass, 1 otherwise (use `SpringApplication.exit` / `System.exit` after the report is printed).
- CI (`.github/workflows/ci.yml`): add a step running the demo command after the tests; a failing scenario must fail the build.

## Classes (package `com.example.payplat.demo`)
- `public class DemoRunner implements ApplicationRunner` (a `@Component`, public no-arg constructor, no injected dependencies; it builds its own Spring contexts). `run(ApplicationArguments)` does nothing unless the non-option args contain `demo`; then it uses a fresh temp directory, calls `run(Path)`, and exits with the code above.
- `public DemoReport run(Path workDir)`: runs all eight scenarios in order and returns the report. It also prints (to `System.out`, via `System.out.println` at call time) the sections described below, and the final line. It must be callable several times in one JVM (no leaked static state) and must close every Spring context it opened before returning.
- `public record DemoReport(List<ScenarioResult> scenarios)` with nested `public record ScenarioResult(int number, String name, boolean passed, String detail, Map<String, Object> facts)`.
  - `DemoReport`: `ScenarioResult scenario(int number)`; `boolean allPassed()` (true iff every listed scenario passed); `String resultLine()` = `DEMO RESULT: ALL SCENARIOS PASSED` when all passed, else `DEMO RESULT: FAILED ` + label of the FIRST failed scenario. `ScenarioResult.label()` = `"[" + number + "] " + name`. Lists and the facts map are unmodifiable copies; `facts` is never null.
  - `detail` is a short human sentence (what was checked); on failure it says what differed.
- Scenario names (exact): 1 `onboard-and-debit`, 2 `duplicate-submit`, 3 `callback-chaos`, 4 `channel-failover`, 5 `partial-success`, 6 `crash-recovery`, 7 `reconciliation-differences`, 8 `monitoring`.
- Everything else (simulator, demo configuration, demo clock) is the executor's design but must follow "Simulator and wiring" below.

## Output contract
For each scenario print a header line that starts with `[n] ` followed by a short title (scenario number n = 1..8, in ascending order, each exactly once), then indented detail lines, then a line `    RESULT: PASS` or `    RESULT: FAIL <detail>`. After scenario 8 print the blank-line-separated final line `report.resultLine()` as the LAST line the demo prints. Spring/logback noise must be reduced to WARN and above (banner off) so the sections are readable. Scenario 1 prints the YAML block of the onboarded channel; scenario 4 prints the persisted switch log; scenario 7 prints each difference; scenario 8 prints the monitoring JSON.

## Simulator and wiring
- A `demo` Spring profile (`@Profile("demo")` configuration) provides, as `@Primary` beans: an in-process synthetic `ChannelGateway` and a settable `Clock` starting at the fixed instant `2026-01-15T10:00:00Z`. The runner starts each scenario's contexts with `spring.profiles.active=demo`, web type NONE, banner off, and `spring.datasource.url=jdbc:h2:file:<workDir>/scenario-<n>/payplat;DB_CLOSE_DELAY=0`, so each scenario has its OWN fresh file database `<workDir>/scenario-<n>/payplat.mv.db` (scenario 6 uses two contexts over the same database file; scenario 1 may use two).
- The simulator is generic: it is driven by `ChannelRegistry` properties (id, latencyMs, ...) and contains no channel-id literal except in the scripting code of the scenarios in `DemoRunner`. It plays FakeBankA, FakeBankB, FakeBankC, FakeWallet and, in scenario 1 onwards, FakeBankD.
- Each `submit` (accepted or rejected) advances the demo clock by the channel's `latencyMs`, so `gateway_call_log.duration_ms` equals the channel latency. `submit` is idempotent per `(channel, orderId)` on the channel side only in the sense of counting: the simulator counts submit calls and accepted debits per order so scenarios can prove "debited once".
- The simulator keeps its own truth ledger per order (accepted / final status / amount) from which `query` and `statement(channel, date)` (UTC date of the demo clock) are answered truthfully, and it can be scripted: reject submits on a channel (reason string), crash the caller right after accepting a given order (throw a simulated crash exception from inside `submit` AFTER the debit is recorded in the ledger), produce callbacks (`ChannelCallback`) that are duplicated / reordered / delayed, and tamper with statements (drop a line, add a phantom line, change an amount, change a status).
- Onboarding by YAML only: add `src/main/resources/demo-channels.yml` = the four channels of `channels.yml` unchanged PLUS exactly one new block `id: FakeBankD` (feeBps 50, latencyMs 50, stability 0.92, successRate 0.95, rateLimitPerSec 100, maintenance false). It is loaded for the demo via `spring.config.additional-location=classpath:/demo-channels.yml` (higher precedence replaces the list). No `.java` file under `src/main` may contain the text `FakeBankD`: the Java code must work for a channel it has never heard of. (Scenario scripts in `DemoRunner` refer to the new channel through facts discovered from the registry, e.g. "the channel that ranks first for FASTEST".)

## Scenarios and required facts
`facts` keys below are mandatory and tested; values are strings, `Long`/`Integer`, booleans, `List` or `Set`/`Map` as shown. Add more keys if useful. A scenario FAILS (passed=false) if any asserted condition is false; it must verify the conditions itself, not just report them. A thrown exception inside a scenario makes that scenario FAIL with the exception message in `detail` (never swallowed, never turned into PASS); the remaining scenarios still run.

1. `onboard-and-debit`: with the 4-channel config the FASTEST tier ranks FakeBankC first (`fastestBefore`); after adding the FakeBankD block (5-channel config) FASTEST ranks FakeBankD first (`fastestAfter`). Submit one 5000-cent task, tier FASTEST, split 1, run the worker, deliver the success callback (sequence 1), the task is `SUCCEEDED`; then `reconcile(clock's UTC date)` is balanced. Facts: `fastestBefore`="FakeBankC", `fastestAfter`="FakeBankD", `chosenChannel`="FakeBankD", `tier`="FASTEST", `callbackOutcome`="APPLIED", `taskStatus`="SUCCEEDED", `reconBalanced`=true, `reconDiffCount`=0.
2. `duplicate-submit`: the same `bizRequestId` submitted twice (and the worker run twice) -> one task, one order, one gateway submit, one debit. Facts: `taskIdFirst`, `taskIdSecond` (equal), `taskCount`=1, `gatewaySubmitCount`=1, `debitCount`=1.
3. `callback-chaos`: one order submitted and SUBMITTED; callbacks delivered in this order: (seq 2, SUCCESS), (seq 1, PROCESSING), (seq 2, SUCCESS) again, (seq 3, FAILED). Facts: `outcomes`=["APPLIED","IGNORED_STALE","DUPLICATE","IGNORED_ILLEGAL"] (the `CallbackOutcome` names in delivery order), `finalOrderStatus`="SUCCESS", `taskStatus`="SUCCEEDED".
4. `channel-failover`: FakeBankD (the FASTEST winner) is scripted down (rejects with reason `CHANNEL_DOWN`). Four tasks (split 1, FASTEST) are submitted and the worker runs. The first three attempts go to FakeBankD, fail and switch to FakeBankC; the circuit opens after the third consecutive failure, so the fourth task never calls FakeBankD. Facts: `downChannel`="FakeBankD", `downChannelSubmitCalls`=3, `switchLogRows`=3, `switches`=List of strings `"<from>-><to>:<reason>"` read from the persisted switch log (3 entries, each `"FakeBankD->FakeBankC:SUBMIT_FAILED"`), `finalChannels`=Set {"FakeBankC"}, `tasksSucceeded`=4 (after the success callbacks are delivered).
5. `partial-success`: one task, 3000 cents, split 3, FASTEST. Callbacks: two orders SUCCESS, one order FAILED. The task is `NOT_FINALIZED`, never `SUCCEEDED`. Facts: `taskStatus`="NOT_FINALIZED", `reason`="partial: 2/3 succeeded", `orderStatuses`=sorted List ["FAILED","SUCCESS","SUCCESS"].
6. `crash-recovery`: one task, 900 cents, split 3, FASTEST, file database. The simulator accepts the debit of the FIRST order and then the process "dies" inside `submit` (simulated crash exception propagates out of `JobWorker.runOnce`; the first context is abandoned/closed without any clean-up code of ours running). A second context starts on the SAME database file with the demo clock advanced beyond the recovery window (121 s). `RecoveryService.recover()` asks the channel first, finds the debit, and resolves the order without submitting again; the worker then processes the remaining orders; after the status-correction window the task is `SUCCEEDED`. Facts: `crashObserved`=true, `crashPoint`="AFTER_ACCEPT", `recoveryResolved`=1, `recoveryRequeued`=0, `orderCount`=3, `submitCallsPerOrder`=List [1,1,1] (ascending order id), `debitsPerOrder`=List [1,1,1], `taskStatus`="SUCCEEDED".
7. `reconciliation-differences`: four orders succeed on one day and reconcile balanced (`balancedBeforeTamper`=true). Then the statements are tampered: order 1's line removed (SHORT), order 2's amount changed (AMOUNT_MISMATCH), order 3's status changed to FAILED (STATUS_MISMATCH), a phantom line for an unknown order id added (LONG). `reconcile` reports exactly those four differences. After the tampering is undone the same date reconciles balanced again and `recon_diff` holds no row for that date. Facts: `balancedBeforeTamper`=true, `balanced`=false, `diffTypes`=Set {"LONG","SHORT","AMOUNT_MISMATCH","STATUS_MISMATCH"}, `diffCountByType`=Map with each of the four types -> 1, `persistedDiffRows`=4, `balancedAfterRestore`=true.
8. `monitoring`: thirty tasks (split 1) spread over the four tiers, with FakeBankD scripted to reject every fourth submit with reason `TIMEOUT`; worker runs; then `MonitoringService.toJson()`. Facts: `json` (the string), `channels`=Set of channel ids in the JSON (at least 3), `p50Ms` and `p95Ms`=Map channelId -> Long, `anyFailureReasons`=true (at least one channel has a non-empty `failureReasons`). Because every submit advances the clock by the channel latency, `p50Ms` equals `p95Ms` for each channel.
